# 事实基线锁定法（事实驱动 · 通用工序）

> **一句话定位**：先采集，后写稿。动笔前把脚本要用的每个硬事实核实进一张表，写稿只准引用表内事实。
> **什么时候用它**：**每次课程必过**——它是动笔前的质量门，数字密集、与代码库强绑定的教程尤其不能省。
> **用法**：本方案是**通用工序**，不参与写作主法的「三选一」（三份主法 `method-goal-contract.md` / `method-audience-persona.md` / `method-block-design.md` 中按症状选一份）。脚本格式规范见同目录 `AUTHORING.md`，通用底线见同目录 `baseline.md`；本文件夹自包含，可整目录交给 LLM 使用。

---

## ① 确定目标

脚本里每一个可核查的断言——数字、行数、版本号、文件名、命令与命令输出、历史事件——都有出处，且与代码库当前状态一致。**进视频前零硬错误**：画面上的大字和旁白念的数，同源同值。受众是会暂停跟练的程序员：他会照着视频敲命令、checkout 对应快照核对行数——他敲不出来的命令、对不上的数字，都是硬错误。

## ② 怎样才能达成

- **先采集，后写稿**：写稿只允许引用表内事实，不允许现场「回忆」数字——LLM 对数字的记忆不可信，这是硬错误的第一来源。
- **口径唯一**：同一事实全系列只定义一次、只用一个表述；画面卡片和旁白必须查同一张表。口径不一会直接自相矛盾：本课程出过 B04 卡片写 149 行、B18 旁白却念 78 行的事故。
- **按跟练视角核实**：上屏/上口的命令以「逐字执行一遍」为核查方式，不只核对输出。

## ③ 具体步骤

1. **建表**：四列——`断言 | 值 | 出处（文件:行）| 核查命令`。按本次课程提纲（这集要讲什么）逐条列出脚本会用到、且仅这些硬事实：文件行数（`wc -l`）、测试通过数（`node --test`）、版本号（`node -v`）、素材时长（`ffprobe`）、历史运行数据（运行记录文档）、上屏/上口命令（核查命令即逐字执行该命令本身）、量化对比主张（「快 N 倍」「省一半」之类，核查命令须是可复现的测量过程，测不出来就不进脚本）。代码状态相关的事实（行数、测试数），出处注明参照快照（如 `l1-talk` tag）；平台相关命令，出处标注实测环境（OS/shell）——MSYS 后台任务（不在 Windows 进程树内、外部杀不干净）就是平台特异的坑，本课程实测踩过。**每条实际执行核查命令后填值**，不填记忆值。核查命令跑不通或出处不存在时，该条标「未核实」——未核实的事实不进脚本：要么修复后重测，要么脚本改述为不依赖该数字的表达。历史事件等无法命令化核查的，核查命令列填人工核对方式（如「对照 `docs/runs/x.md` 第 20 行逐字比对」）。
2. **冻结口径**：每个事实选定一个表述，全系列只用它；有口径歧义的（如「l1-talk 标签下 78 行 vs 现状 149 行」）在表里写清适用语境。**含数字的事实同时冻结两种形式**：上屏形式（画面卡片写法，如 `149`）与上口形式（旁白念法，如「一百四十九行」）——可在表中加两列；TTS 对阿拉伯数字与混排（`21*2`）读法不可控，英文/混排词（版本号、命令）的上口读法走发音词典（AUTHORING §4.5），此类词的上口形式格填「见发音词典」，旁白里保留原文。
3. **写稿引用**：脚本只用表内事实——画面文字逐字取「上屏形式」格，旁白逐字取「上口形式」格，不改写、不约数、不换单位。「逐字一致」指逐字取自对应表格，不是把同一串字同时塞进画面和旁白。事实表全系列共用一张，存系列公共位置（如 `<系列公共目录>/facts.md`），各集追加新条目。
4. **成稿双向核对**：脚本全量扫描数字与文件名，逐条对表——对不上表的事实只有两条路：补做核查填进表，或从脚本删去该说法；表内被引用条目逐条回查脚本，发现表述漂移就统一。列出全部不一致项，修到零才算过。
5. **敏感信息同工序处理**：token、内网地址、真实用户名在建表阶段即替换为占位符——本课程出过素材示例残留明文 token、画面 HTML 暴露真实用户名的事故。
6. **持续维护**：代码或文档变更后重跑核查命令更新表；下次写稿从最新表出发。

## 给 LLM 的提示词模板

> 空位（`___` 与【】）由发令方填写后使用；留空时执行方先自行盘点相关路径、列出待确认清单，再开始。

```
动笔前先读：【课程提纲（这集要讲什么）：___】【路径清单（本集涉及的仓库源码 / 参考文档 / 运行记录的具体路径）：___】。
先不要写脚本。通读上述路径，按提纲产出一张事实表：
断言 | 值 | 出处（文件:行）| 核查命令 | 上屏形式 | 上口形式。
只收提纲涉及的数字、行数、版本、命令输出、历史事件与上屏/上口命令（逐字执行验证），每条实际执行核查命令后填值；
代码状态相关的事实出处注明参照快照（git tag/commit），平台相关命令标注实测环境（OS/shell）；跑不通核查命令的标「未核实」（不进脚本）；含数字的一并冻结「上屏形式」与「上口形式」。
事实表存系列公共位置（如 `<系列公共目录>/facts.md`，全系列共用一张）：若该表已存在，先重跑表内核查命令刷新值，再追加本集新条目。
等我确认事实表后再开始写脚本。写脚本时只允许使用表内事实：画面文字逐字用「上屏形式」、旁白逐字用「上口形式」，不改写、不约数。
脚本完成后做双向核对：脚本中每个数字对表，表中每个被引用条目回查脚本，列出所有不一致项并逐条修正（补核查进表，或从脚本删改），直到不一致项为零。
```

## 通用底线（任何方案都必须守）

> 已单文件化：见同目录 [`baseline.md`](baseline.md)，十条底线全系列共用，任何方案交稿前都必须逐条过。改底线只改 `baseline.md` 一处。

## 依据

- 内部教训：本课程曾交付带硬数据错误的成片、同一视频里数字自相矛盾（卡片 149 行 vs 旁白 78 行）——没做本工序的直接代价。
- 内部教训：凭记忆沿用的数字会稳定地错——本课程改写稿时抓出过把约 120 行记成 78 行、把 1200 行记成 1100 行的错误，只有逐条回源核对才抓得到。
