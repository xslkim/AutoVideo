# 双角色评审迭代法（质量驱动 · 通用工序）

> **一句话定位**：脚本定稿后、交音画验收之前，开两个视角对立的评审 agent——学员保「能跟上、能学会」，专家保「质量、深度、广度」——必改项清零才放行。
> **什么时候用它**：**代码精讲类系列每次必过**（SoftGpu EP02–07 重构即靠它收敛）；写作主法三选一完成之后、音画验收工序之前执行。一般内容可裁剪为单角色。
> **用法**：本方案是**通用工序**，插在两道既有通用工序之间：事实基线（动笔前）→ 写作主法 → **双角色评审** → 音画验收（交构建前）。脚本格式规范见同目录 `AUTHORING.md`，通用底线见同目录 `baseline.md`；本文件夹自包含，可整目录交给 LLM 使用。

---

## ① 确定目标

脚本同时通过两种互相牵制的检验：学员视角下**全程可跟随**（每个新概念有铺垫、每段代码有前置图解、没有「听到这句必须回放三遍」的点）；专家视角下**事实零错误、口径全系列唯一、深度广度配得上主题**。两种视角的**必改项全部修完**、复审确认后，脚本才允许进构建。

## ② 怎样才能达成

- **两个角色的输入不对称，这是工序的核心**：
  - **学员 agent 只读 `narration.md` 旁白纯文本**（可对照块标题），不给 plan.md / facts.md / visuals.md——观众看片时不知道的他也不许知道。他模拟线性观看，报告每一个「跟不上」的时间点：新概念无铺垫、指代悬空、代码块没有前置图解、一句话塞两个新东西。
  - **专家 agent 读全部稿件 + facts.md + 被引用的源码**：逐条抽查事实表里的 file:line 引用是否属实，查深度广度（该讲的机制层级有没有缺）、查口径（同一说法在全系列各集是否唯一，如「GPU 到提交才开工」不许一处说「上电就开工」）。
- **评审输出分级**：每条意见标 **必改**（事实错误、学员必掉队、口径冲突——阻断构建）或 **建议**（锦上添花）。修订方只被强制约束必改项，但要对每条建议给出采纳/不采纳的一句话理由。
- **至少两轮**：第 1 轮评审 → 修订 → 第 2 轮复审（原角色各来一遍，重点核对必改项是否真修了、修订有没有引入新问题）。第 2 轮仍有必改项就再迭代；**连续一轮零必改项才放行**。
- **并行开 agent**：每集开学员、专家各一个（多集可复用同一角色 agent 的上下文，但各集稿件必须独立评审），评审结论落盘 `reviews/round{N}-{student,expert}.md`，与脚本同目录。
- **修订要三处同步**：旁白、visuals.md 描述、plan/facts 里的时长与口径数字，改一处必须查另外两处（真实教训：旁白改了「第四站提交才开工」，visuals 角标和 plan 里还留着旧说法）。

## ③ 具体步骤

1. **备齐评审包**：narration.md + visuals.md（学员只看前者）；专家另加 plan.md / facts.md / dict.md 与 facts.md 里列出的源码路径清单。
2. **发评审令**：按文末提示词模板，学员、专家各发一份；每集两个 agent 并行。
3. **汇总裁决**：收齐 round1 两份报告，列出必改项清单；建议项逐条标采纳/不采纳。
4. **修订**：逐项修，修完跑一遍 compile 预检（结构错误早发现）；时长与口径变了就同步 plan.md / facts.md。
5. **复审**：round2 同角色再审一遍；零必改项 → 进音画验收工序；仍有必改项 → 回到步骤 3。
6. **归档**：两轮报告留 `reviews/` 目录随脚本进 git——下一集评审时学员/专家 agent 可先读上集报告，避免重复踩坑。

## 给 LLM 的提示词模板

> 空位（`___` 与【】）由发令方填写后使用。

学员角色：

```
你是零基础跟随型学员，会暂停、会记笔记，但不会回放三遍以上。
只准读【narration.md 路径：___】的旁白纯文本（可对照 >>> 块标题），
不许假设自己看过计划文档、事实表或画面描述。
模拟线性看完整集，逐块回答：① 这块我听懂了吗？② 每个新词第一次出现时有没有一句人话解释？③ 有没有指代悬空（"这个/它"指不到前文）？④ 读代码的块之前，我有没有先在旁白里拿到心智模型？⑤ 哪一句我需要回放才能跟上？
输出：按块列「必改（必掉队）/ 建议」，每条给原句和改法。报告存【reviews/round___-student.md】。
```

专家角色：

```
你是该领域专家，负责知识的质量、深度、广度。
读【narration.md / visuals.md / plan.md / facts.md 路径：___】，并抽查 facts.md 中每条 file:line 引用对照【源码根：___】核实。
逐块检查：① 事实与源码是否一致（字段数、调用顺序、行号）；② 机制讲到的层级是否配得上主题（该深的浅了算必改）；③ 全系列口径唯一性（同一概念的说法/数字与【前集脚本目录：___】是否冲突）；④ 深浅失衡点（哪里啰唆、哪里跳步）。
输出：按块列「必改（事实错/口径冲突/深度缺口）/ 建议」。报告存【reviews/round___-expert.md】。
```

## 依据

- 内部：SoftGpu 系列 EP02（拆上中下）、EP05/06/07（拆上下）重构全部经过本工序两轮迭代收敛；命中的典型必改项包括：读代码块前缺图解块、ICD 结构体字段数与源码不符、同一句机制在三处文件三种说法、上电与 ring 编程两步混为一步。
- 与既有工序的关系：学员角色是 `process-av-acceptance.md`「纯音频通读」的前置强化版（把可懂性五查提前到结构还可大改的阶段）；专家角色是 `process-fact-baseline.md` 的回访（事实表写完后再对照源码抽查一遍）。
